# ADR 0023 — Chat: a real SQL parser shared by browser and server, a server-counted tool loop, and priced messages

**Status:** accepted · **Date:** 2026-09-13 · **Phase:** 8

## Context

The relevant SPEC sections are §2.3, §2.7–2.9, §7, §12, §27 and §34 Phase 8. They require:

- **Message types:** chat with the MIS as Quick, Deep, Edit and Investigate messages. The type is the price, and the send button shows it.
- **Quick:** a deterministic retriever over the metric store.
- **Deep:** a `run_query` tool loop over session data that exists only in the browser, with a server-enforced round cap.
- **Edit:** JSON Patch proposals with preview, apply and undo.
- **SQL guard:** built on a real SQL parser and shared by server and browser. It allows one SELECT over session tables only and denies statements, table functions and URLs. LIMIT is enforced, and the guard is fuzz-tested against malicious corpora.
- **Threads:** a thread caps at 20 messages and continues from a summary whose cost is absorbed by the next message.
- **Charging:**
  - out-of-scope requests are declined in one sentence and charged;
  - Quick and Edit reserve and capture a fixed price;
  - Deep reserves the full price, captures on answer, and releases on platform failure.
- **Acceptance:**
  - the guard blocks the malicious corpus;
  - the round cap is enforced server-side;
  - an out-of-scope decline is charged per policy;
  - placeholders resolve with lineage.

## Decisions

### 1. The SQL guard is an allowlist AST walk over libpg-query, in its own package

- **Package:** `@magicmis/sql-guard` runs unchanged on the server and in the pipeline worker. It is a separate package so the browser pipeline does not depend on chat's server code; that dependency formed a cycle.
- **What is allowed:**
  - exactly one `SelectStmt`;
  - AST node types, functions and cast types each from an allowlist;
  - relations: the session tables, `main.` only, or CTEs defined in the query. This also rejects replacement scans such as `FROM 'x.csv'`, `FROM x.csv` and `FROM "x.csv"`, which parse as ordinary relations.
- **What is refused:** `SELECT INTO`, locking clauses, comments, control characters, string literals that look like URLs or file paths, and anything that fails to parse.
- **LIMIT:** enforced by wrapping as `SELECT * FROM (<query>) AS guarded_query LIMIT <cap + 1>`. The wrapped text is parsed and checked again before it runs.
- **Tests:** a malicious corpus (69 cases: every denied statement, stacked statements, table functions, replacement scans, catalogs, dangerous functions, URLs, `SELECT INTO`, arrays), legitimate analytical queries, and property tests. The property tests embed forbidden constructs in random SQL-like positions (2,000 runs) and throw arbitrary strings at the guard (3,000 runs).
- **Defence in depth:** the browser runs Deep queries in a separate DuckDB instance that holds only the session tables. After loading, it sets `enable_external_access = false` and `lock_configuration = true`. A test proves that the locked instance refuses `read_csv`, `COPY` and re-enabling access, even for SQL that never went through the guard.
- **Timeout:** the browser query timeout uses `cancelSent()`.

### 2. Deep is one server round per request; the cap counts stored steps

- **Tools:** `chatDeepStep` offers two strict tools, `run_query` and `answer`, and forces exactly one call per round. When stored steps reach `chat.max_rounds`, it forces `answer`.
- **Conversation state:** rebuilt each round from `chat_query_steps` (tool-use id, SQL, purpose and result, sealed under the company key). The browser can neither add rounds nor alter earlier results.
- **Guard rejections:** a query the server's guard rejects is stored as a rejected step. It spends a round and goes back to the model as an error tool result.
- **Accepted queries:** go to the browser as `needs_query`. The browser guards the query again, runs it, redacts every cell, and caps rows and bytes. The server validates the result's schema, row count, ragged rows and byte size, and runs `assertNoRawIdentifiers`, before continuing.
- **Answers:**
  - Checked by `checkPlaceholderTexts`, V12 generalised in `@magicmis/engine`. It adds `{{q:<step>:<row>:<column>}}`, which must point inside a stored result. One repair, then a platform fault.
  - Query cells carry lineage: SQL, purpose, and the session tables the guard saw.
- **Model misbehaviour:** a model that still calls `run_query` at the cap is refused, repaired once, and failed with the hold released.

### 3. Quick and Edit are structured-output stages; Edit applies separately

- **Quick:** `chatQuick` gets the facts that `retrieveFacts` picks deterministically, using metric vocabulary from the template catalogue and period words relative to the latest stored month. The placeholder IDs are the same as the commentary facts pack. The answer schema carries `scope`; an out-of-scope reply must be one sentence.
- **Edit:** `chatEditSpec` returns operations with values as JSON text (structured outputs cannot express arbitrary JSON values). The stage check requires:
  - the operations parse;
  - every metric ID is allowed;
  - the patch validates against the dashboard or template schema.
- **Applying an edit:** a separate confirmation using the operations stored with the reply, never operations sent by the browser.
  - Dashboard edits use the Phase 7 version store.
  - Template edits record `editedFrom`, so undo restores the earlier template as a new version.
  - The patch engine moved to `@magicmis/core/json-patch` and is shared by both.

### 4. Pricing, holds and threads

- **Holds:** a message is priced (type × tier, from the price book) and held before any AI call. The cost cap is price × `max_ai_cost_ratio`.
- **Settlement:**
  - an answer or an out-of-scope decline captures the price;
  - AI failures (stage error, routing, runtime cap) release it.
- **Abandoned messages:** a message left waiting past its hold is swept, released and marked `abandoned` (R-43).
- **Threads:** a thread caps at `chat.thread_message_cap`. The next message opens a continuation thread whose first message generates the summary; its AI call is recorded against that message and so counts towards its cap. History is sent in a cached block.
- **Chat `max_tokens` re-seeded (migration 0024), a margin fix found by the tests:**
  - The 0019 values could not run. A professional Quick call (Sonnet 5, 8,000 tokens) projected about ₹8 against a ₹3.80 cap.
  - New values: Quick and Deep rounds 1,500; Edit 2,000; summaries 1,000. At the seeded prices every tier's single call fits its cap.
  - A worst-case Deep message (five large rounds) can still exceed its cap and then fails without a charge (R-42).

### 5. A fake model for browser tests, development only

- **What:** `AI_TRANSPORT=fake` gives the web server a deterministic transport that returns only outputs the real stages accept. The Playwright suite uses it to drive Quick, out-of-scope, Deep (with a real browser query) and Edit through the UI.
- **Restriction:** it is refused unless `NEXT_PUBLIC_ENVIRONMENT=development`, the same rule as the local key wrapper (R-45).
- **Scope:** it is not an Anthropic client and lives outside `packages/ai`.

### 6. Parser WebAssembly in the bundles

- **Browser:**
  - `libpg-query.wasm` is self-hosted under `/vendor/pg` and copied at build, like DuckDB's files.
  - Bundled, Emscripten resolves the file to a bare relative name. A shim imported first in the pipeline worker redirects that request.
- **Server:** `libpg-query` is a server external package, so Node loads the WebAssembly from `node_modules`.

## Consequences

- **Acceptance evidence:** `packages/sql-guard/test/guard.test.ts` (guard), `packages/chat/test/server.test.ts` (round cap, out-of-scope charge, lineage, holds, thread cap, sweep), `packages/pipeline/test/chat.test.ts` (browser queries and the locked DuckDB), `packages/render-dashboard/test/answer.test.ts` (rendering and re-check) and `apps/web/e2e/mis.spec.ts` (chat through the UI).
- **Activation:** `chat_quick`, `chat_edit` and `thread_summary` have eval datasets. `chat_deep` needs an eval harness that can drive a tool loop before its prompt can be activated (R-44).
- **Streaming:** the final answer is not streamed. SPEC §27 allows streaming but does not require it.
